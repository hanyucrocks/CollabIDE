# Deploying CollabIDE

Backend on Render, frontend on Vercel, database on MongoDB Atlas — the split the
TRD calls for. The backend needs a host that keeps WebSocket connections open,
which rules out pure-serverless platforms for that half.

## Before you start

- **MongoDB Atlas** free M0 cluster
- **Render** account (or Railway — see the free-tier note below)
- **Vercel** account
- The repo pushed to GitHub; both hosts deploy from it

## The ordering trap

The two services each need the other's URL:

- the API must allow the frontend's origin (`CLIENT_ORIGIN`)
- the frontend must know the API's URL (`VITE_API_URL`)

Neither URL exists until its service is created, so deploy in this order:

1. Backend first, with a placeholder `CLIENT_ORIGIN` — note its URL
2. Frontend, with `VITE_API_URL` set to that URL — note its URL
3. Go back and set the real `CLIENT_ORIGIN` on the backend

**`VITE_*` variables are inlined at build time, not read at runtime.** Changing
one in the Vercel dashboard does nothing until you redeploy.

## 1. MongoDB Atlas

1. Create a free **M0** cluster.
2. **Database Access** → add a user with a password.
3. **Network Access** → allow `0.0.0.0/0`. Render's free tier has no static
   outbound IPs, so an allowlist cannot be narrowed usefully here.
4. **Connect → Drivers** → copy the connection string and append the database
   name: `.../collabide?retryWrites=true&w=majority`.

Without the database name, Mongo writes to `test`, which works and then quietly
confuses you later.

## 2. Backend on Render

`render.yaml` at the repo root describes the service, so **New → Blueprint** and
pointing Render at the repo picks it up.

Set the two secrets marked `sync: false` in the dashboard:

| Variable | Value |
| --- | --- |
| `MONGO_URI` | the Atlas string from step 1 |
| `CLIENT_ORIGIN` | `http://localhost:5173` for now |

`JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` are generated by Render and persist
across deploys. Rotating either invalidates every issued token — which is the
point, but it logs everyone out.

Confirm with `curl https://<your-api>.onrender.com/api/health` → `{"ok":true}`.

**`NODE_VERSION` must stay at 24 or higher.** The server runs TypeScript through
Node's native type stripping, unflagged only from 23.6 on. An older Node fails at
startup, not at build, so the deploy looks successful and the service crash-loops.

## 3. Frontend on Vercel

**New Project** → same repo → set **Root Directory** to `client`. `vercel.json`
supplies the rest.

Add one environment variable before the first build:

| Variable | Value |
| --- | --- |
| `VITE_API_URL` | `https://<your-api>.onrender.com` |

Do **not** set `VITE_WS_URL`. The client derives the socket URL from
`VITE_API_URL`, turning `https` into `wss` in the same rewrite. Setting it by
hand is how deployments end up on `ws://` against an HTTPS page: browsers block
that as mixed content, and the symptom is the editor silently never syncing
while every other part of the app works.

## 4. Close the loop

Back on Render, set `CLIENT_ORIGIN` to the Vercel URL (no trailing slash) and
redeploy. Multiple origins are comma-separated, which is how you keep preview
deployments working:

```
https://collabide.vercel.app,https://collabide-git-main-you.vercel.app
```

## Verifying

1. `curl https://<api>/api/health` → `{"ok":true}`
2. Open the frontend, sign up, create a room. The badge should read
   **connected** — if it says *connecting* forever, the WebSocket is failing;
   check the browser console for a mixed-content or 403 error.
3. Copy the invite link, open it in a **different browser profile**, sign up as a
   second user. Type in one window and confirm it appears in the other.
4. Reload one tab. The document should come back — that is the snapshot being
   read from Atlas.

Step 4 is the one that proves the whole stack: it only passes if Atlas, the
persistence layer, and the WebSocket are all working together.

## Verifying against the deployed server

The smoke suite can be pointed at production, which is a far better check than
clicking through the app:

```bash
cd server
SMOKE_API_URL=https://your-api.onrender.com MONGO_URI="<atlas uri>" npm run smoke
```

It creates `@collabide.test` accounts and removes them when it finishes.

One behaviour differs through a proxy and is worth knowing: when an owner
demotes a member, the server closes that member's sockets so the client
reconnects with its new role. The *close frame* can be delayed by the platform's
proxy well past the point where writes are already being refused, so the client
may still report itself connected for several seconds. The guarantee — that a
demoted member cannot write — holds throughout; only the client's awareness of
the close lags.

## Free-tier realities

**Render free services sleep after ~15 minutes of inactivity.** Every WebSocket
drops and the next request waits ~30 seconds for a cold start. Yjs reconnects and
resyncs on its own, so nothing is lost — the snapshot is written on
last-peer-disconnect — but it is a poor demo if a viewer arrives cold, and wrong
for a live interview. Railway has no sleep and no free tier; that is the trade.

**Atlas M0 has no backups.** Fine for a demo, not for anything you would miss.

**Rooms are deleted after 30 days of inactivity**, along with their snapshots,
to stop abandoned rooms filling a finite tier. Rooms with someone connected are
never swept. Set `ROOM_TTL_DAYS` to change the window or `0` to turn it off.

## Configuration reference

**Server** (Render dashboard):

| Variable | Required | Notes |
| --- | --- | --- |
| `MONGO_URI` | yes | include the database name |
| `CLIENT_ORIGIN` | yes | comma-separated, no trailing slashes |
| `JWT_ACCESS_SECRET` | yes | generated by Render |
| `JWT_REFRESH_SECRET` | yes | generated by Render |
| `NODE_ENV` | yes | `production` — enables `trust proxy` |
| `NODE_VERSION` | yes | 24+ |
| `PORT` | no | assigned by Render |
| `ACCESS_TOKEN_TTL` | no | default `15m` |
| `REFRESH_TOKEN_TTL` | no | default `7d` |

**Client** (Vercel, build time):

| Variable | Required | Notes |
| --- | --- | --- |
| `VITE_API_URL` | yes | no trailing slash |
| `VITE_WS_URL` | no | derived from `VITE_API_URL`; leave unset |

## Enabling code execution

Execution is stubbed until `JUDGE0_URL` is set. That one variable decides
whether runs are real; a key is only needed by deployments that ask for one.

**Public Judge0 instance** — no account, no key:

| Variable | Value |
| --- | --- |
| `JUDGE0_URL` | `https://ce.judge0.com` |

**RapidAPI gateway** — if you have a key:

| Variable | Value |
| --- | --- |
| `JUDGE0_URL` | `https://judge0-ce.p.rapidapi.com` |
| `JUDGE0_API_KEY` | your RapidAPI key |

Set these on the API service, never as `VITE_*` variables. Anything with that
prefix is compiled into the browser bundle, where every visitor can read it.
The client asks *this* API to run code; only the server talks to Judge0.

`ce.judge0.com` is a public instance run by the Judge0 maintainers. It is
best-effort: no SLA, undocumented limits, and it could throttle or disappear.
That is a reasonable trade for a demo and a poor one for anything that depends
on it — if this becomes more than a demo, either pay for the hosted service or
self-host, which the TRD already names as the V2 direction.

Until `JUDGE0_URL` is set, runs return a labelled stub rather than failing, so
the rest of the app can be shown without any execution service.

## Not yet handled
- **The access token travels as a WebSocket query parameter**, because browsers
  cannot set headers on a WS handshake. Query strings are prone to appearing in
  proxy logs. The token is short-lived, which limits the exposure rather than
  removing it.
- **The rate limiter is in-process.** Correct for one instance; behind several
  the effective limit multiplies by the instance count.
